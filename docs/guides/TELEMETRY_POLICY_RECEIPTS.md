# Telemetry budget policy receipts

Status: immutable policy-receipt slice reviewed and qualified with the full Go suite, dashboard cycle and actual workflows in both authentication profiles. This delivers the first part of [TEL-1](../FEATURE_COMPLETION_SPEC.md#tel-1-immutable-policy-and-time-coverage). Full TEL-1–TEL-4 remain open for qualified clocks, source-loss evidence, time coverage, telemetry verdicts and complete reporting.

When managed execution commits INITIALIZING, the controller stores complete initial configuration and resolved telemetry budgets in that same Start transaction before asynchronous runtime staging. Pending admission does not fabricate a receipt. Candidates stay private while SQL waits. Failed writes do not pin settings; successful retries adopt the write-once durable winner, including legacy absent-policy receipts. Later system settings do not rewrite retained run budgets.

Unless the run chose a budget policy (below), the receipt identifies apexload.telemetry_policy.v1, fixed policy system-telemetry-budgets revision 1, semantic SHA-256, UTC capture time and legacy-mixed-diagnostic.v1. Revision 1 identifies the fixed contract, not a global settings edit counter. Capture time is provenance excluded from the digest. Five stages preserve sample age, generator processing, transport, controller fan-out and browser render budgets. Nil resolves existing defaults; explicit zero disables a stage. The existing 15-second sustained window is retained. Actual controller cadence is configured whole seconds for local execution or the existing one-second distributed coalescing gate; it does not certify generator/browser cadence.

Live status, manifests, archive analysis and report execution details (under **Configuration and infrastructure evidence**) show the receipt. Dashboard WebCrypto verifies exact semantic identity before displaying available evidence; pending, malformed or unverifiable receipts remain unavailable, with stale completion fenced. Zero capture time is invalid even with a matching digest; nonzero nanosecond precision is retained. A matching digest detects content mismatch but does not attest origin. Live badges describe observed age or separate controller cumulative drop observations, not exact run loss or a health verdict. Archive interval classifications are explicitly legacy mixed diagnostic; missing summary/counts are n/a, explicit zero stays zero.

```bash
apexctl analysis telemetry-policy --id RUN_ID --mode live
apexctl analysis telemetry-policy --id RUN_ID --mode archive
```

Live mode reads the authorized run manifest; archive mode reads its report. Optional --api and --project retain existing conventions. Unsupported filters, excessive bytes, redirects, project mismatch and malformed canonical fields/digests are refused. Output is a closed projection; raw controller errors and credential values are not printed. Old evidence has no invented policy identity.

## Choosing a budget policy

A run can set its live budgets from one of its project's telemetry budget policies (`telemetry_policy`) instead of the system threshold settings: `telemetry_budget_policy_id` on `POST /api/v1/tests` or `POST /api/v1/ci/runs` (`apexctl ci run --telemetry-budget-policy`, action input `telemetry-budget-policy`). Without a choice the run keeps the system receipt. The project's default budget policy is still only pinned, as before; it does not set a run's budgets.

- **The receipt.** At Start the chosen policy's current revision replaces the system receipt in the same write. The receipt is `apexload.telemetry_policy.v2` and names the policy's ID, its revision and its definition digest (`definition_sha256`). Cadence, cadence scope, capture time and the classification algorithm stay the controller's. Each stage takes the policy's limit, a stage the policy leaves unset uses the built-in default (as in re-evaluation), and a stage set to `0` is disabled. The run's budget pin has source `run_selection`.
- **Live classification** uses the receipt, so the chosen budgets decide which telemetry time is degraded or breached, and with it a telemetry acceptance policy's breached-time criterion.
- **The sustained window** of live classification is fixed at 15 seconds. A policy that sets another `sustained_window_seconds` cannot set a run's budgets and is refused as invalid.
- **At creation**, the policy must be one of the run's own project's live, valid budget policies: one the project lacks is refused (`400`), an invalid or unusable one with `409`, and a failed read gets `503` (retry).
- **CI runs** may choose only where the project's GitHub Actions policy sets `allow_telemetry_policy_selection`, the same permission as the acceptance choice, because looser budgets can loosen a `fail_ci` acceptance policy (otherwise `403`). The CI response echoes the choice, and `apexctl` stops a run whose create response does not echo it and exits with a configuration error. An exact retry of an accepted CI run returns that run even if its choice was since disallowed or deleted.
- **Revised copies** keep their source's choice unless they name another, or `project_default` for the system threshold settings. The dashboard's revise dialog cannot name either yet, so a revise there always keeps the choice; only the API can drop it.
- **At Start**, a chosen policy that is gone or no longer usable refuses Start rather than falling back to the system settings; a direct Start leaves the run queued.
- **Remote runs** forward the choice. A remote controller that does not echo it would classify the run by its system settings, so its run is deleted before it starts and the create is refused (`409`).
- **Readers.** apexctl and the dashboard accept and verify both receipt versions; the dashboard labels a chosen policy as such and shows its definition digest. An older reader never presents a version 2 receipt as the system settings: an older dashboard shows it as unsupported, and an older apexctl refuses it as an invalid receipt.

## Stage distributions and client render evidence

Each run keeps a bounded, mergeable t-digest (compression 100) for every telemetry stage it samples: generator processing, transport (generator to controller), controller fan-out, end-to-end sample age and browser render. Live metrics report `telemetry.stage_distributions` on the current snapshot only (history points and archived interval rows carry none): per stage its sample count, `measured` or `unavailable`, P50/P95/P99/max where it was sampled, and the observations kept out by reason. Stage percentiles are never added together; end-to-end sample age is its own stage. Transport and a distributed run's sample age enter their distributions only while the generator's clock is qualified, otherwise they count as `clock_unqualified`. Each generator batch is sampled once, when the controller accepts it (whether or not it is published on its own), however often it is re-aggregated. At finalize the manifest records `telemetry_stage_distributions` and the mergeable `telemetry_stage_digests`. The distributions live in the sampling controller's memory: each reports `sampled_from`, and a controller that adopted the run after a failover or restart samples only from then (the card says so when that is more than a minute after the run started). A run finalized by a controller that never sampled it records every stage as `unavailable` with reason `recorder_lost`; that includes a run that ended before publishing anything, since the recorder starts with the first sample. An adjunct refresh never adds `recorder_lost` to an archive finalized before stage sampling existed. The Telemetry observations card shows the table.

Browser render is opt-in per project. An editor turns on **Client render evidence** in Settings → Projects → Limits (`PUT /api/v1/projects/{id}/telemetry-policy` with `{"client_render_evidence": true}`; it changes nothing else in the project). Dashboard tabs viewing that project's live runs then measure sampled local live receipts with the browser monotonic clock, from handling the received metrics to a post-commit animation-frame/timer callback and send batches to `POST /api/v1/tests/{id}/telemetry/client-render`. The endpoint needs viewer access to the run's project, accepts at most 64 samples and 16 KiB per report and one report every 2 seconds per tab, within a budget of 8 samples per second (bursts up to 64) per viewer across all their tabs, spent by every visible or unnamed sample and by at least one per report, so new tab identities buy no more samples or reports (429 with `Retry-After`; a named publication's unmeasured outcome spends none: it reaches the stage only from the reference tab, at most one report every 2 seconds; an unauthenticated viewer is identified by address). It answers 409 when the project has not opted in or the run is not live, and 503 on a controller replica that is not the execution leader. Only a sample whose tab stayed visible through the callback counts; background, disconnected, superseded, stalled (over 60 s), implausibly timed and malformed samples are counted as exclusions instead (a named publication's unmeasured outcome only for the reference tab, below). A receipt already known to include a hidden interval is not measured; a pending callback that completes after a hidden interval reports background. The opt-in changes only through its own route: a general project update keeps it, whatever copy of the settings it sends. Browser render is advisory: it sets `browser_render_lag_ms` to the visible p95 for display and summaries, but it is never a run-health condition, and its absence never affects a run, including an unattended CLI run. The browser render budget stays in the policy receipt for compatibility.

Wall time labels the observation only. The callback is a paint opportunity, not proof that a frame was visibly presented. Repeated renders of the same local receipt cannot add another sample; history/wire timestamps alone cannot create one. Unnamed receipts, tabs other than the run's reference tab, queue limits and refused or failed reports remain best-effort gaps in the stage's samples; the render population below covers only the reference tab's own gaps, as unreported publications within its range, and neither establishes an end-to-end SLA.

Every live point a controller publishes names itself in `telemetry.publication`: the controller's publication `epoch` for the run (a controller that adopts the run, or reloads it after a restart, starts another), a `sequence`, `eligible` and, when the point reports a collection time, the oldest and newest collection times it includes (`oldest_collected_at`, `newest_collected_at`, each on its generator's clock, qualified as `sample_age_quality` says; a collection covers the window that ends then). A point is eligible when it carries a collection no earlier point carried: a distributed point whose every generator window was already published (a lifecycle or replayed envelope), or a local point repeating the previous collection time, is not. A reporting tab (one view of the run page) reports the named publications it receives by identity, best effort: `visible` with its measurement when it rendered, `superseded` when a newer publication was rendered before it, and `background` when it was received or painted while the tab was hidden. Unmeasured outcomes are sent only once the tab has measured a visible render (those received earlier are reported with it); receipts that arrived while reporting was off are dropped rather than reported, except the one on screen as reporting starts, which is measured (its interval includes the time reporting was off); a publication delivered again after its first copy was reported is not reported again, and one delivered twice before is never reported superseded by its own copy; a receipt without a name is measured as before. A malformed publication name refuses the report. The run's reference client is the first tab (a viewer's tab identifier, so another viewer cannot report as it) whose report includes a visible render of a publication the controller still holds in the current epoch; it is exposed only as an opaque `reference_client` identifier. `telemetry.render_population` (on the current snapshot, never on history rows, and `telemetry_render_population` in the archive manifest) declares the population, `rendered_publications`, and accounts every eligible publication in the range of sequences the reference client reported: `rendered`, `superseded`, `unqualified` (by reason, for example `background_tab` or `stalled_render`) or `unreported` (never reported by that tab: not delivered, received while its reporting was off or refused, or lost to a failed report or a queue limit; a gap at either end of the range shortens the range instead). These are delivery outcomes, separate from accepted-record loss. It also counts every eligible publication of the epoch (`published_eligible`, viewed or not), and the reference client's reports about ineligible publications (`ineligible`) or that the controller cannot place (`unknown`: another epoch, a publication older than the 4,096 most recent, which it no longer holds, or a sequence it never published; a publication is accounted before it leaves the 4,096, so no accounting is lost). The reference tab's unmeasured outcomes count as `browser_render` exclusions (so with a hidden or busy reference tab the advisory criterion's bounds are often inconclusive); another tab's do not, while any tab's measured samples, and its visible renders refused as stalled or implausibly timed, still enter the advisory stage. The reference tab is chosen, not declared: the first to report a render, which may later be hidden. The run report's telemetry acceptance section states the archived population in HTML and PDF, and each of its figures in the CSV (`telemetry_render_population`). The accounting lives in the publishing controller's memory: one that adopts the run starts a new epoch and accounts from then, records when it began (`sampled_from`), and the report then says its publications were counted since then rather than in all. It identifies and accounts the population; it does not prove visible presentation, qualify browser clocks or establish the capture-to-render SLA.

## Comparing runs and re-evaluating under a common policy

A saved baseline comparison judges each baseline's whole-run telemetry against the current run's in **Telemetry compatibility**. Health is compared only when both runs were classified alike: the same receipt budgets (browser render, which is advisory, aside), sustained window, publication cadence and scope, telemetry source capabilities (source epochs, clock qualification for a distributed run, coverage algorithm), workload keys of the same version and a qualified workload. A local run's clock observations (from monitoring collectors) are not a capability, since they never classified it. Receipts that differ only in the advisory budget are comparable, and the export line then names both policy hashes. A comparable pair shows the change in breached classified intervals, health coverage and breached known-time fraction; any other pair shows both runs' profiles side by side with the reasons. The same verdicts appear in the comparison's HTML, PDF and CSV exports.

To compare runs that were classified differently, re-evaluate them under one project `telemetry_policy` revision. The comparison view's **Re-evaluate** button, or:

```bash
apexctl analysis telemetry-reevaluate --project PROJECT --runs CURRENT,BASELINE --policy POLICY_ID --revision 3 --wait
```

queues a `telemetry_acceptance` evaluation (`POST /api/v1/analysis/evaluations`). It re-scores the retained interval lag evidence of each run with the live rules: a zero or absent budget disables a stage (absent budgets resolve to the built-in defaults, not to today's settings), a cross-host stage needs a qualified clock or the interval is unscored, an interval in which no generator reported a sample has no sample-age decision, and a condition becomes a breach after the policy's sustained window. An interval is healthy only when at least one enabled stage was judged within its budget; one with nothing to judge is unscored (`interval:no_scored_stage`). Whether a run's telemetry crossed hosts comes from its receipt's cadence scope, else its generator source epochs or shards on generators (local runtime-resource shards run in the controller). A run that retained no telemetry, whose interval spacing is longer than the window, or with no classifiable interval (`no_classifiable_intervals`) is reported as unanswerable rather than healthy. Intervals archived before the sample-less marker existed (`sample_age_unavailable`) cannot be told apart, so a distributed run's sample-less windows from then are unscored. The result is a separate, hashed artifact whose input fingerprint covers the policy revision and each run's archive manifest; the archives and their original classifications are never changed. Only the lag budgets are re-scored, so the original counts (which also included drop and transaction diagnostics) are context, not a like-for-like delta.

## Telemetry acceptance verdicts

A project `telemetry_acceptance_policy` judges a run's telemetry, apart from its application verdict. The policy that applies by default is pinned when the run starts, and its definition is frozen in the admission receipt beside the pin (`provenance.telemetry_acceptance_policy`), so a later edit never reinterprets the run.

A run can instead choose one of its project's acceptance policies by ID: `telemetry_acceptance_policy_id` on `POST /api/v1/tests` (`apexctl run --api … --telemetry-policy`, the dashboard's revise modal) or `POST /api/v1/ci/runs` (`apexctl ci run --telemetry-policy`, action input `telemetry-policy`). A scenario can choose one for every run created from it (`telemetry_acceptance_policy_id` on the scenario; the scenario builder's Advanced settings).
- **At creation**, the policy must be one of the project's live, valid acceptance policies:
  - one the project lacks is refused (`400`);
  - an invalid one is refused with `409`;
  - a failed read gets `503` (retry).
- **CI runs** may choose only where the project's GitHub Actions policy sets `allow_telemetry_policy_selection`. Otherwise a choice is refused (`403`), so a pipeline cannot exchange a `fail_ci` default for a weaker policy. Naming `project_default` is no choice and needs no permission. The CI response echoes the choice. `apexctl` stops a run whose create response does not echo it, and exits with a configuration error. An exact retry of an accepted CI run returns that run even if its choice was since disallowed or deleted.
- **Revised copies.** A revised copy of a queued run keeps its source's choice unless it names another, or `project_default` to use the project's default.
- **Scenarios.** A scenario's choice is validated when it is saved with a new choice, against the scenario's own project's policies, with the same answers as at run creation. A save that keeps the current choice, within the same project, is not judged again, so an unrelated edit, an import or a rollback never fails on it.
  - **Inheritance.** Every run created from the scenario inherits the choice: a direct run, a schedule and an execution-plan entry, unless the run names another or `project_default`.
  - **A deleted choice** refuses the inheriting run and names the scenario's choice, rather than judging the run by the default. A scheduled occurrence refused this way is recorded as failed. If the policies cannot be read while such a run is created (a schedule, a plan entry or a direct run naming no policy), the run is still created with the scenario's choice, which was validated when it was saved and which Start pins or refuses. Start reads the project's policies for every run, so a run started during the outage is refused at Start as any run would be.
  - **Not portable.** The choice is project-local. A library bundle omits it, a new import uses its destination's default, and an import that updates a linked scenario keeps that scenario's choice. A remote run of such a scenario must name the remote policy or `project_default` (otherwise `409`), because the remote judges the run by its own copy's choice or its project's default, never by the local choice.
- **Plain CLI runs.** `apexctl run --api … --telemetry-policy ID` sends the choice and requires the create response to echo it.
  - **Not echoed.** The queued run is deleted before Start and `apexctl` exits with a configuration error (`2`). If the delete cannot be confirmed (the run can still be read, or the confirming read fails), the run may still be queued: `apexctl` names it and exits `3`.
  - **Refused.** A controller refusal of the choice itself (`400` or `409` naming the telemetry acceptance policy: missing, over-long or invalid) is also exit `2`.
  - The flag needs `--api`.
- **At Start**, the chosen policy's current revision is pinned with source `run_selection`, in place of the default. A chosen policy that is gone or invalid by Start refuses Start, as an invalid default does, rather than falling back to the default. A direct Start leaves the run queued.
- **Default changes.** Changing the project's default never changes a run's choice.
- **Remote runs** forward the choice to the remote controller, which checks it against the remote project's policies. A remote controller that does not echo the choice would judge the run by its project's default, so its run is deleted before it starts and the create is refused (`409`).

A policy's criteria are optional, but at least one is required:

| Criterion | Evidence | Passes when |
| --- | --- | --- |
| `min_wall_time_coverage` | `telemetry_coverage`: observed ÷ window wall time | observed ≥ floor |
| `max_lost_records` | `telemetry_loss.dropped_results` | lost ≤ ceiling |
| `max_loss_ratio` | lost ÷ (lost + recorded results) | ratio ≤ ceiling |
| `max_breached_known_time_fraction` | breached ÷ classified telemetry time | fraction ≤ ceiling |
| `stage_lag_percentiles` | `telemetry_stage_distributions` p50/p95/p99/max | value ≤ `max_ms` |

The verdict is `pass`, `fail` or `inconclusive`. Any failed criterion fails the verdict. A criterion whose evidence is missing, or whose evidence is a lower bound that could still be within its limit, is inconclusive. Unknown required evidence never passes. Loss counts are lower bounds, never exact, when either of these holds:

- a lost publication or a dropped subscriber batch lost an unknown number of records;
- a counter cannot rule such a loss out.

A stage percentile is judged on the whole run's distribution. When a controller adopted the run after a failover, it sampled stages only from the adoption: that maximum is a lower bound (a maximum already above the limit fails), and any other percentile of part of the run bounds nothing (`partial`), so the criterion is inconclusive. When observations were excluded (an unqualified clock, an invalid value), the excluded ones could lie anywhere, so the whole run's percentile is only bounded: by the kept distribution's quantiles at the two ranks it could hold, read from the archived stage digest (a live, provisional verdict uses the nearest recorded kept percentiles instead, which bound it less tightly). The criterion passes when the value it could rise to, if every excluded observation was slower, is within the limit (`upper_bound`, shown as ≤), and fails when the value it could fall to, if every excluded one was faster, exceeds it (`lower_bound`, shown as ≥). Otherwise it is inconclusive; a maximum with any exclusion has no upper bound. `browser_render` is reported by viewers' open tabs, so its criterion is shown as advisory and never decides the verdict.

A distributed run finalized without its source ledger (after a restart, or by a controller that never executed it) records every loss counter as unavailable (`ledger_lost`); after an adoption, the recovered and current source ledger supplies the counters, and generations absent from that ledger make them lower bounds. Its wall-time coverage counts the time it could not observe as unknown and says why (`telemetry_coverage.coverage.observer_lost`: `ledger_lost` when the run was finalized without its source ledger, after a restart or by a controller that never executed it; `adopted` after a controller takeover, including when earlier committed spans were recovered; live coverage says `adopted` too), so observed time is a lower bound: below the floor `min_wall_time_coverage` is inconclusive, never a failure. The policy stage `generator` is the generator-processing distribution. `end_to_end` (capture to a viewer's render) has no measured distribution yet, so it is always inconclusive. Shed arrivals are a workload shortfall, and the WebSocket drop counters are controller-wide, so neither is counted as telemetry loss.

New coverage records use `telemetry_coverage.v3`. Duplicate or late publication envelopes and repeated collection identities do not add observation time at their later receipt. The first accepted terminal publication retires the source; stale epochs and repeated terminal envelopes cannot move that boundary. Publication/loss evidence still retains late and duplicate arrivals. Reaching the bounded source-epoch ledger makes coverage a lower bound: a below-floor result is inconclusive. Coverage remains a receipt-time approximation, with bounded jitter bridging only between consecutive fresh window publications; qualified source-clock coverage remains open; durable checkpoint recovery is described below. Legacy sources without collection identities retain receipt-window behavior, so their distinct envelopes cannot be proven to carry distinct collections. Existing archives keep their original algorithm and evidence; baseline comparisons disclose differing algorithms rather than comparing their classifications. See the [implementation evidence](../qa/reviews/roadmap-telemetry-coverage-2026-10-19/README.md).

Generators also retain bounded, per-group result-buffer drain intervals on their published clock, independently of the effective or clamped `WindowMs` rate denominator. Nanosecond boundaries travel in `MetricsBatch.collection_windows` and are retained with source epoch, execution generation and collection sequence in generator archive telemetry JSON (including Parquet’s `telemetry_json`). Lifecycle replays keep the same collection intervals; only groups actually collected contribute new intervals. Missing, malformed or bounded-out intervals leave `collection_windows_complete` false. This means completeness of the reported drain cohort, not qualified cross-host coverage, request start/end times, or proof of controller delivery. The receipt-time coverage calculation stays at v3.

Controllers checkpoint accepted collection identities, cumulative run totals, source publication/counter ledgers, receipt-time coverage and bounded source windows together. The checkpoint belongs to the run incarnation and execution generation; execution-lease fencing and increasing revisions reject stale writers. During HA adoption, compatible checkpoints restore cursors and their counted effects together instead of rebuilding totals from sampled history. A replay of a retained collection cannot add totals or move coverage into the takeover gap. Stored collection evidence is not proof of dashboard delivery. Only runs whose failover policy is `continue` (the runs HA adoption can resume) write checkpoints. A terminal run is never adopted again: the terminal status write removes its checkpoint payload in the same transaction, and the revision is kept so no stale writer can restore it.

The controller retains the latest 1,024 identified collections, with at most 4,096 group intervals across them. Eviction is explicit. The checkpoint has an 8 MiB limit; a failed or oversized write leaves the prior durable snapshot intact. Retained windows, policy hashes and available cumulative loss-counter readings also appear in the source-epoch archive sidecar. Its byte allowance trims optional window detail before existing source/counter records and marks that detail incomplete. Original generator archive evidence remains unchanged.

Missing, incompatible or unreadable checkpoints retain legacy unknown/lower-bound recovery. Unknown checkpoint versions are not overwritten by this controller. Recovery does not fill unobserved gaps or make raw generator timestamps clock-qualified. Collection classification remains unknown; the admission policy hash binds the existing policy and cadence receipt, without inventing an in-run revision. Policy segmentation and qualified capture-to-render correlation remain separate work.

The run manifest now records its loss totals at finalize as `telemetry_loss`. The verdict appears in four places:

- **Live:** while the run executes, the Telemetry observations card shows it as provisional (`telemetry.acceptance`). It updates as evidence arrives, and the breached-time criterion stays inconclusive until finalize. A finished run, or one whose live health was rebuilt from stored history (a restarted controller, a follower), shows no provisional verdict: its verdict is the archived one in the run report.
- **Run report:** the **Telemetry Acceptance** section in HTML, PDF, DOCX and CSV. It lists the policy revisions, each criterion with its observed value, bound and denominator, exact or lower-bound loss counters, coverage by source, classified time, clock quality, stage distributions with their exclusions, and what the verdict does not count. The report JSON carries it as `telemetry_acceptance`.
- **Saved baseline comparisons:** each run's verdict and dropped results, side by side. Each run was judged by its own pinned revision, so verdicts are shown, never compared.
- **Webhooks:** a finalized run whose pinned verdict failed or was inconclusive publishes a bounded, scrubbed `telemetry_acceptance` event through the durable delivery path below. The event identifies the run, policy revision, deciding non-advisory criteria and sources with unknown time, stamped with the run's completion time. A run in mode `unknown` is not announced.

Telemetry evidence carries text into these projections: generator source and target names, policy names and descriptions, counter and stage reasons, exclusion and render reasons, and the verdict text built from them. Each projection scrubs it. Reasons, descriptions and verdict text get the runs' own redaction rules (the scenario's and each group's, each distinct rule once; a rule that no longer compiles is skipped, not the others) and then the shared credential scrubber (credentials and tokens in URLs, sensitive query values, `password=`-style pairs, tokens). Policy names get the same rules and the scrubber's label form, which keeps a long name. Generator targets, IDs and source names, and keys such as states, exclusion reasons, policy IDs, criterion IDs and the policy's mode and lag stages, get only the label form: run rules are payload rules, and one masking addresses would make every generator look alike (a real key passes unchanged). Control and bidirectional formatting characters become spaces. When the runs hold more than 1,024 distinct rules, rule-scrubbed text is withheld rather than shown. The archive manifest's public projection (the run report's JSON, HTML, PDF, DOCX and CSV, the manifest view, safe archive export and the browser diagnostics bundle) scrubs it for both the run's and its admission provenance, together with generator targets in its source coverage, shard and inventory entries and host-network sources. The report's generator-assignment appendix, the test manifest view and the safe export's test manifest scrub every generator target they list the same way (selected, shard and inventory targets, in the generator lists, both configurations, their groups and the scripts), as does the archive manifest for the run's and each group's selected targets; the report's completeness finding and the run calendar's topology name generators that way. Verdicts are judged on the recorded evidence and only their text is scrubbed, in the report, CI output (its response and check summary) and the notification sent where the durable outbox is unavailable. A baseline comparison is decided on the recorded profiles and shown scrubbed with both runs' rules; one saved before this change is shown with the shared scrubber. The archive keeps what was recorded: its telemetry sidecars (`telemetry_sources`, clock observations) and resource samples name generators as recorded, and so do the validity findings the report shows. The durable notification envelope keeps its own scrubbing (the full scrubber, which can blank a long generator name). A safe export's manifest bytes change once with this projection: a library bundle listed before the upgrade, or by a controller on the earlier version, declares the earlier manifest hash, so importing an archive exported now for it fails its hash check until the bundle is exported again.

`mode` is `advisory` by default: the verdict never changes a CI outcome. Under `fail_ci` it can fail an otherwise passed CI run; see [CI telemetry acceptance](../CICD_INTEGRATION.md#telemetry-acceptance-gate). A run that pinned a policy before definitions were frozen has an inconclusive verdict in mode `unknown`, which no gate enforces. Advisory telemetry never stops a run.


## Durable acceptance notifications

With the default SQLite or PostgreSQL store, archive catalog publication and the
notification decision commit in one transaction against the exact verified final
manifest. This includes recovery from an uploaded archive after its local source
is lost. A crash before commit retains the archive intent; a crash after commit
leaves delivery pending. Outcome identity binds the project, run incarnation,
policy revision, assessment digest and verdict. Repeating that identity reuses
its original payload and recipient set. A later assessment can publish a distinct
outcome without rewriting the old event.

The envelope is at most 64 KiB, including metadata, with at most 32 events per
run and 64 configured destinations per event. Run/source text is scrubbed with
the retained run rules and the shared credential scrubber, then bounded. URLs
and tokens are not stored in the envelope: opaque keyed fingerprints pin the
complete authorized webhook configuration. Identical configurations collapse
into one destination; event-filter order does not matter. A changed, disabled or
removed configuration revokes its pending delivery rather than redirecting it.
Recipients are read from the durable settings at publication and again before
each send. A webhook whose stored configuration does not validate on this
controller (for example one saved by a peer with a different outbound or
cleartext policy) is skipped; it neither blocks the archive commit nor
suppresses the other recipients. A failed configuration read remains retryable. A no-recipient decision stays
empty even if webhooks are enabled later.

The execution leader polls once per second. Preparation and completion observers
are limited to 16; sends reuse the existing 16 global and two-per-destination-stripe
dispatcher slots. A claim lasts 60 seconds, with at most eight durable attempts
and exponential backoff capped at one minute. Each admitted dispatch retains the
existing HTTP retry policy, so an attempt is not necessarily one HTTP request.
Dispatcher saturation sends nothing, so it returns the claimed attempt and retries
about a second later. Transport failure and interrupted delivery remain retryable
until the attempt budget is exhausted. Successful destinations are not retried with failed
ones. Successful shutdown cancels and joins the storage-writing observers; a shutdown
deadline error is not proof that all owned work has joined. Exact lease and
run-incarnation checks reject stale or deleted work immediately before dispatch;
a request already admitted to an external receiver cannot be recalled.

The stable receiver idempotency key survives retries. Delivery is **at least once**:
a receiver that does not honor the key can receive duplicates after an ambiguous
HTTP completion. A lease timeout is never proof that the receiver did nothing.

Inspect delivery state through the run's telemetry-notification operation in
[Swagger](../swagger.yaml), `GET /api/v1/tests/{id}/telemetry/notifications`.
It requires viewer access to that project (service accounts need `results:read`)
and returns no payload, destination or credentials. The current publication
summary includes the manifest digest, fixed decision, event identity when one
was retained, and cumulative suppressed-publication count. Its delivery counts
cover all retained outcomes for that run: `pending`, `leased`, `delivered`,
`exhausted` and `revoked`. The decision `enqueued` describes publication, not the
current delivery state. `no_recipients`, `not_applicable`, `projection_rejected`,
`identity_unavailable`, `capacity_exhausted` and `legacy_claim` explain other
outcomes. Capacity or unsafe-projection refusal is durably visible without
blocking the archive forever. The bounded summary is not a history of every
rejected payload. A legacy run with no retained decision reports `not_recorded`;
unsupported custom storage reports unavailable.

Old timestamp claims have unknown delivery results and are not blindly replayed.
New events install a compatibility marker so older claim-based controllers do not
announce that outcome again. Custom archive stores without the complete atomic
capability keep the legacy claim-before-dispatch behavior, including its lost-send
limitation. Test/project deletion removes notification state with the run.

The [runtime review](../qa/reviews/roadmap-telemetry-notification-runtime-2026-10-20/README.md)
retains local crash, SQL, authorization, sanitization, retry and shutdown evidence.
It does not qualify external receiver exactly-once behavior or multi-host recovery.

[Review and qualification](../qa/reviews/feature-completion-telemetry-policy-2026-10-05/README.md) separates actual SQL/client checks from remaining scope. Source epochs, clock qualification, wall-time coverage, exact/lower-bound loss and a single policy segment per run have since been implemented (Feature completion Waves 1 and 2) but not qualified; stage distributions, opt-in client render evidence and policy-compatible comparison with re-evaluation (Wave 3), and acceptance verdicts that are advisory or fail CI apart from the application verdict (Wave 4), are implemented as described above; qualified per-interval source-clock coverage and complete exports remain open. The under-two-second figure remains a design target pending declared hardware/workload acceptance.
