# Telemetry budget policy receipts

Status: immutable policy-receipt slice reviewed and qualified with the full Go suite, dashboard cycle and actual workflows in both authentication profiles. This delivers the first part of [TEL-1](../FEATURE_COMPLETION_SPEC.md#tel-1-immutable-policy-and-time-coverage). Full TEL-1–TEL-4 remain open for qualified clocks, source-loss evidence, time coverage, telemetry verdicts and complete reporting.

When managed execution commits INITIALIZING, the controller stores complete initial configuration and resolved telemetry budgets in that same Start transaction before asynchronous runtime staging. Pending admission does not fabricate a receipt. Candidates stay private while SQL waits. Failed writes do not pin settings; successful retries adopt the write-once durable winner, including legacy absent-policy receipts. Later system settings do not rewrite retained run budgets.

The receipt identifies apexload.telemetry_policy.v1, fixed policy system-telemetry-budgets revision 1, semantic SHA-256, UTC capture time and legacy-mixed-diagnostic.v1. Revision 1 identifies the fixed contract, not a global settings edit counter. Capture time is provenance excluded from the digest. Five stages preserve sample age, generator processing, transport, controller fan-out and browser render budgets. Nil resolves existing defaults; explicit zero disables a stage. The existing 15-second sustained window is retained. Actual controller cadence is configured whole seconds for local execution or the existing one-second distributed coalescing gate; it does not certify generator/browser cadence.

Live status, manifests, archive analysis and report execution details (under **Configuration and infrastructure evidence**) show the receipt. Dashboard WebCrypto verifies exact semantic identity before displaying available evidence; pending, malformed or unverifiable receipts remain unavailable, with stale completion fenced. Zero capture time is invalid even with a matching digest; nonzero nanosecond precision is retained. A matching digest detects content mismatch but does not attest origin. Live badges describe observed age or separate controller cumulative drop observations, not exact run loss or a health verdict. Archive interval classifications are explicitly legacy mixed diagnostic; missing summary/counts are n/a, explicit zero stays zero.

```bash
apexctl analysis telemetry-policy --id RUN_ID --mode live
apexctl analysis telemetry-policy --id RUN_ID --mode archive
```

Live mode reads the authorized run manifest; archive mode reads its report. Optional --api and --project retain existing conventions. Unsupported filters, excessive bytes, redirects, project mismatch and malformed canonical fields/digests are refused. Output is a closed projection; raw controller errors and credential values are not printed. Old evidence has no invented policy identity.

## Stage distributions and client render evidence

Each run keeps a bounded, mergeable t-digest (compression 100) for every telemetry stage it samples: generator processing, transport (generator to controller), controller fan-out, end-to-end sample age and browser render. Live metrics report `telemetry.stage_distributions` on the current snapshot only (history points and archived interval rows carry none): per stage its sample count, `measured` or `unavailable`, P50/P95/P99/max where it was sampled, and the observations kept out by reason. Stage percentiles are never added together; end-to-end sample age is its own stage. Transport and a distributed run's sample age enter their distributions only while the generator's clock is qualified, otherwise they count as `clock_unqualified`. Each generator batch is sampled once, when the controller accepts it (whether or not it is published on its own), however often it is re-aggregated. At finalize the manifest records `telemetry_stage_distributions` and the mergeable `telemetry_stage_digests`. The distributions live in the sampling controller's memory: each reports `sampled_from`, and a controller that adopted the run after a failover or restart samples only from then (the card says so when that is more than a minute after the run started). A run finalized by a controller that never sampled it records every stage as `unavailable` with reason `recorder_lost`; that includes a run that ended before publishing anything, since the recorder starts with the first sample. An adjunct refresh never adds `recorder_lost` to an archive finalized before stage sampling existed. The Telemetry observations card shows the table.

Browser render is opt-in per project. An editor turns on **Client render evidence** in Settings → Projects → Limits (`PUT /api/v1/projects/{id}/telemetry-policy` with `{"client_render_evidence": true}`; it changes nothing else in the project). Dashboard tabs viewing that project's live runs then measure each publication from WebSocket receipt to the first paint after it rendered and send batches to `POST /api/v1/tests/{id}/telemetry/client-render`. The endpoint needs viewer access to the run's project, accepts at most 64 samples and 16 KiB per report and one report every 2 seconds per tab, within a budget of 8 samples per second (bursts up to 64) per viewer across all their tabs, so new tab identities buy no more samples (429 with `Retry-After`; an unauthenticated viewer is identified by address). It answers 409 when the project has not opted in or the run is not live, and 503 on a controller replica that is not the execution leader. Only a visible tab's render counts; background, disconnected, stalled (over 60 s), implausibly timed and malformed samples are counted as exclusions instead. A tab that is hidden when an update arrives does not measure it, and one hidden at any point before it painted the update reports the render as background. The opt-in changes only through its own route: a general project update keeps it, whatever copy of the settings it sends. Browser render is advisory: it sets `browser_render_lag_ms` to the visible p95 for display and summaries, but it is never a run-health condition, and its absence never affects a run, including an unattended CLI run. The browser render budget stays in the policy receipt for compatibility.

## Comparing runs and re-evaluating under a common policy

A saved baseline comparison judges each baseline's whole-run telemetry against the current run's in **Telemetry compatibility**. Health is compared only when both runs were classified alike: the same receipt budgets (browser render, which is advisory, aside), sustained window, publication cadence and scope, telemetry source capabilities (source epochs, clock qualification for a distributed run, coverage algorithm), workload keys of the same version and a qualified workload. A local run's clock observations (from monitoring collectors) are not a capability, since they never classified it. Receipts that differ only in the advisory budget are comparable, and the export line then names both policy hashes. A comparable pair shows the change in breached classified intervals, health coverage and breached known-time fraction; any other pair shows both runs' profiles side by side with the reasons. The same verdicts appear in the comparison's HTML, PDF and CSV exports.

To compare runs that were classified differently, re-evaluate them under one project `telemetry_policy` revision. The comparison view's **Re-evaluate** button, or:

```bash
apexctl analysis telemetry-reevaluate --project PROJECT --runs CURRENT,BASELINE --policy POLICY_ID --revision 3 --wait
```

queues a `telemetry_acceptance` evaluation (`POST /api/v1/analysis/evaluations`). It re-scores the retained interval lag evidence of each run with the live rules: a zero or absent budget disables a stage (absent budgets resolve to the built-in defaults, not to today's settings), a cross-host stage needs a qualified clock or the interval is unscored, an interval in which no generator reported a sample has no sample-age decision, and a condition becomes a breach after the policy's sustained window. An interval is healthy only when at least one enabled stage was judged within its budget; one with nothing to judge is unscored (`interval:no_scored_stage`). Whether a run's telemetry crossed hosts comes from its receipt's cadence scope, else its generator source epochs or shards on generators (local runtime-resource shards run in the controller). A run that retained no telemetry, whose interval spacing is longer than the window, or with no classifiable interval (`no_classifiable_intervals`) is reported as unanswerable rather than healthy. Intervals archived before the sample-less marker existed (`sample_age_unavailable`) cannot be told apart, so a distributed run's sample-less windows from then are unscored. The result is a separate, hashed artifact whose input fingerprint covers the policy revision and each run's archive manifest; the archives and their original classifications are never changed. Only the lag budgets are re-scored, so the original counts (which also included drop and transaction diagnostics) are context, not a like-for-like delta.

## Telemetry acceptance verdicts

A project `telemetry_acceptance_policy` judges a run's telemetry, apart from its application verdict. The policy that applies by default is pinned when the run starts, and its definition is frozen in the admission receipt beside the pin (`provenance.telemetry_acceptance_policy`), so a later edit never reinterprets the run. Its criteria are optional, but at least one is required:

| Criterion | Evidence | Passes when |
| --- | --- | --- |
| `min_wall_time_coverage` | `telemetry_coverage`: observed ÷ window wall time | observed ≥ floor |
| `max_lost_records` | `telemetry_loss.dropped_results` | lost ≤ ceiling |
| `max_loss_ratio` | lost ÷ (lost + recorded results) | ratio ≤ ceiling |
| `max_breached_known_time_fraction` | breached ÷ classified telemetry time | fraction ≤ ceiling |
| `stage_lag_percentiles` | `telemetry_stage_distributions` p50/p95/p99/max | value ≤ `max_ms` |

The verdict is `pass`, `fail` or `inconclusive`. Any failed criterion fails the verdict. A criterion whose evidence is missing, or whose evidence is a lower bound that could still be within its limit, is inconclusive. Unknown required evidence never passes. Loss counts are lower bounds, never exact, when either of these holds:

- a lost publication or a dropped subscriber batch lost an unknown number of records;
- a counter cannot rule such a loss out.

A stage percentile is judged on the whole run's distribution. When a controller adopted the run after a failover, it sampled stages only from the adoption: that maximum is a lower bound (a maximum already above the limit fails), and any other percentile of part of the run bounds nothing (`partial`), so the criterion is inconclusive. When observations were excluded (an unqualified clock, an invalid value), the excluded ones could lie anywhere, so the whole run's percentile is only bounded: by the kept distribution's quantiles at the two ranks it could hold, read from the archived stage digest (a live, provisional verdict uses the nearest recorded kept percentiles instead, which bound it less tightly). The criterion passes when the value it could rise to, if every excluded observation was slower, is within the limit (`upper_bound`, shown as ≤), and fails when the value it could fall to, if every excluded one was faster, exceeds it (`lower_bound`, shown as ≥). Otherwise it is inconclusive; a maximum with any exclusion has no upper bound. `browser_render` is reported by viewers' open tabs, so its criterion is shown as advisory and never decides the verdict.

A distributed run finalized without its source ledger (after a restart, or by a controller that never executed it) records every loss counter as unavailable (`ledger_lost`); after an adoption, the adopting controller's ledger supplies the counters, and generations it never observed make them lower bounds. Its wall-time coverage counts the time it could not observe as unknown and says why (`telemetry_coverage.coverage.observer_lost`: `ledger_lost` when the run was finalized without its source ledger, after a restart or by a controller that never executed it; `adopted` when a controller adopted the run and observed it only from then; live coverage says `adopted` too), so observed time is a lower bound: below the floor `min_wall_time_coverage` is inconclusive, never a failure. The policy stage `generator` is the generator-processing distribution. `end_to_end` (capture to a viewer's render) has no measured distribution yet, so it is always inconclusive. Shed arrivals are a workload shortfall, and the WebSocket drop counters are controller-wide, so neither is counted as telemetry loss.

The run manifest now records its loss totals at finalize as `telemetry_loss`. The verdict appears in four places:

- **Live:** while the run executes, the Telemetry observations card shows it as provisional (`telemetry.acceptance`). It updates as evidence arrives, and the breached-time criterion stays inconclusive until finalize. A finished run, or one whose live health was rebuilt from stored history (a restarted controller, a follower), shows no provisional verdict: its verdict is the archived one in the run report.
- **Run report:** the **Telemetry Acceptance** section in HTML, PDF, DOCX and CSV. It lists the policy revisions, each criterion with its observed value, bound and denominator, exact or lower-bound loss counters, coverage by source, classified time, clock quality, stage distributions with their exclusions, and what the verdict does not count. The report JSON carries it as `telemetry_acceptance`.
- **Saved baseline comparisons:** each run's verdict and dropped results, side by side. Each run was judged by its own pinned revision, so verdicts are shown, never compared.
- **Webhooks:** a finalized run whose verdict failed or was inconclusive sends one `telemetry_acceptance` event per outcome. A durable claim, deleted with the run, keeps a later attach of the same archive (a refresh, a recovered publication, another leader) from announcing that outcome again; a verdict a refresh found changed is announced. A dispatch lost after its claim is not retried. The event's conditions name the run, the policy revision, the deciding criteria that did not pass (never advisory ones) and the sources with unknown time, and it is stamped with the run's completion time. A run in mode `unknown` is not announced.

`mode` is `advisory` by default: the verdict never changes a CI outcome. Under `fail_ci` it can fail an otherwise passed CI run; see [CI telemetry acceptance](../CICD_INTEGRATION.md#telemetry-acceptance-gate). A run that pinned a policy before definitions were frozen has an inconclusive verdict in mode `unknown`, which no gate enforces. Advisory telemetry never stops a run.
