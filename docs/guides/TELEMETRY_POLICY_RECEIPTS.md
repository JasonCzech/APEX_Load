# Telemetry budget policy receipts

Status: immutable policy-receipt slice reviewed and qualified with the full Go suite, dashboard cycle and actual workflows in both authentication profiles. This delivers the first part of [TEL-1](../FEATURE_COMPLETION_SPEC.md#tel-1-immutable-policy-and-time-coverage). Full TEL-1–TEL-4 remain open for qualified clocks, source-loss evidence, time coverage, telemetry verdicts and complete reporting.

When managed execution commits INITIALIZING, the controller stores complete initial configuration and resolved telemetry budgets in that same Start transaction before asynchronous runtime staging. Pending admission does not fabricate a receipt. Candidates stay private while SQL waits. Failed writes do not pin settings; successful retries adopt the write-once durable winner, including legacy absent-policy receipts. Later system settings do not rewrite retained run budgets.

The receipt identifies apexload.telemetry_policy.v1, fixed policy system-telemetry-budgets revision 1, semantic SHA-256, UTC capture time and legacy-mixed-diagnostic.v1. Revision 1 identifies the fixed contract, not a global settings edit counter. Capture time is provenance excluded from the digest. Five stages preserve sample age, generator processing, transport, controller fan-out and browser render budgets. Nil resolves existing defaults; explicit zero disables a stage. The existing 15-second sustained window is retained. Actual controller cadence is configured whole seconds for local execution or the existing one-second distributed coalescing gate; it does not certify generator/browser cadence.

Live status, manifests, archive analysis and report execution details show the receipt. Dashboard WebCrypto verifies exact semantic identity before displaying available evidence; pending, malformed or unverifiable receipts remain unavailable, with stale completion fenced. Zero capture time is invalid even with a matching digest; nonzero nanosecond precision is retained. A matching digest detects content mismatch but does not attest origin. Live badges describe observed age or separate controller cumulative drop observations, not exact run loss or a health verdict. Archive interval classifications are explicitly legacy mixed diagnostic; missing summary/counts are n/a, explicit zero stays zero.

```bash
apexctl analysis telemetry-policy --id RUN_ID --mode live
apexctl analysis telemetry-policy --id RUN_ID --mode archive
```

Live mode reads the authorized run manifest; archive mode reads its report. Optional --api and --project retain existing conventions. Unsupported filters, excessive bytes, redirects, project mismatch and malformed canonical fields/digests are refused. Output is a closed projection; raw controller errors and credential values are not printed. Old evidence has no invented policy identity.

## Stage distributions and client render evidence

Each run keeps a bounded, mergeable t-digest (compression 100) for every telemetry stage it samples: generator processing, transport (generator to controller), controller fan-out, end-to-end sample age and browser render. Live metrics report `telemetry.stage_distributions` on the current snapshot only (history points and archived interval rows carry none): per stage its sample count, `measured` or `unavailable`, P50/P95/P99/max where it was sampled, and the observations kept out by reason. Stage percentiles are never added together; end-to-end sample age is its own stage. Transport and a distributed run's sample age enter their distributions only while the generator's clock is qualified, otherwise they count as `clock_unqualified`. Each generator batch is sampled once, when the controller accepts it (whether or not it is published on its own), however often it is re-aggregated. At finalize the manifest records `telemetry_stage_distributions` and the mergeable `telemetry_stage_digests`. The distributions live in the sampling controller's memory: each reports `sampled_from`, and a controller that adopted the run after a failover or restart samples only from then (the card says so when that is more than a minute after the run started). A run finalized by a controller that never sampled it records every stage as `unavailable` with reason `recorder_lost`. The Telemetry observations card shows the table.

Browser render is opt-in per project. An editor turns on **Client render evidence** in Settings → Projects → Limits (`PUT /api/v1/projects/{id}/telemetry-policy` with `{"client_render_evidence": true}`; it changes nothing else in the project). Dashboard tabs viewing that project's live runs then measure each publication from WebSocket receipt to the first paint after it rendered and send batches to `POST /api/v1/tests/{id}/telemetry/client-render`. The endpoint needs viewer access to the run's project, accepts at most 64 samples and 16 KiB per report and one report every 2 seconds per tab, within a budget of 8 samples per second (bursts up to 64) per viewer across all their tabs, so new tab identities buy no more samples (429 with `Retry-After`; an unauthenticated viewer is identified by address). It answers 409 when the project has not opted in or the run is not live, and 503 on a controller replica that is not the execution leader. Only a visible tab's render counts; background, disconnected, stalled (over 60 s), implausibly timed and malformed samples are counted as exclusions instead. A tab that is hidden when an update arrives does not measure it, and one hidden at any point before it painted the update reports the render as background. The opt-in changes only through its own route: a general project update keeps it, whatever copy of the settings it sends. Browser render is advisory: it sets `browser_render_lag_ms` to the visible p95 for display and summaries, but it is never a run-health condition, and its absence never affects a run, including an unattended CLI run. The browser render budget stays in the policy receipt for compatibility.

## Comparing runs and re-evaluating under a common policy

A saved baseline comparison judges each baseline's whole-run telemetry against the current run's in **Telemetry compatibility**. Health is compared only when both runs were classified alike: the same receipt budgets (browser render, which is advisory, aside), sustained window, publication cadence and scope, telemetry source capabilities (source epochs, clock qualification for a distributed run, coverage algorithm), workload keys of the same version and a qualified workload. A local run's clock observations (from monitoring collectors) are not a capability, since they never classified it. Receipts that differ only in the advisory budget are comparable, and the export line then names both policy hashes. A comparable pair shows the change in breached classified intervals, health coverage and breached known-time fraction; any other pair shows both runs' profiles side by side with the reasons. The same verdicts appear in the comparison's HTML, PDF and CSV exports.

To compare runs that were classified differently, re-evaluate them under one project `telemetry_policy` revision. The comparison view's **Re-evaluate** button, or:

```bash
apexctl analysis telemetry-reevaluate --project PROJECT --runs CURRENT,BASELINE --policy POLICY_ID --revision 3 --wait
```

queues a `telemetry_acceptance` evaluation (`POST /api/v1/analysis/evaluations`). It re-scores the retained interval lag evidence of each run with the live rules: a zero or absent budget disables a stage (absent budgets resolve to the built-in defaults, not to today's settings), a cross-host stage needs a qualified clock or the interval is unscored, an interval in which no generator reported a sample has no sample-age decision, and a condition becomes a breach after the policy's sustained window. An interval is healthy only when at least one enabled stage was judged within its budget; one with nothing to judge is unscored (`interval:no_scored_stage`). Whether a run's telemetry crossed hosts comes from its receipt's cadence scope, else its generator source epochs or shards on generators (local runtime-resource shards run in the controller). A run that retained no telemetry, whose interval spacing is longer than the window, or with no classifiable interval (`no_classifiable_intervals`) is reported as unanswerable rather than healthy. Intervals archived before the sample-less marker existed (`sample_age_unavailable`) cannot be told apart, so a distributed run's sample-less windows from then are unscored. The result is a separate, hashed artifact whose input fingerprint covers the policy revision and each run's archive manifest; the archives and their original classifications are never changed. Only the lag budgets are re-scored, so the original counts (which also included drop and transaction diagnostics) are context, not a like-for-like delta.
