Headline items:

### W1 (CRITICAL) lr.AUTO transaction status resolves to PASS despite errors — Java false-success reintroduced

**Where:** `runners/java_vuser/lrapi/lr.java:440` · **Area:** infra · **Category:** correctness · **Verification:** 2/2 verifiers confirmed

end_transaction/end_sub_transaction now route an AUTO (default) status through resolveTransactionStatus, which returns transactionStatus.getOrDefault(name, PASS). Nothing ever records failure into that map when errors occur during the transaction: lr.error_message() only emits an 'error' event (and the Go adapter's finalizeResult merely counts error events in an extraction, it never fails the run on them), and lr.set_transaction_status() emits but does not write to the transactionStatus map. In LoadRunner, LR_AUTO fails the transaction if an error was raised during it. Before this diff, the raw AUTO value (2) was emitted and pkg/protocol/java_vuser/java_vuser.go failedRunnerTransactions() treated any non-zero status as failed, so these runs at least surfaced as failures (over-eagerly). After this diff the standard LR error-handling pattern reports transaction PASS and overall run success — the exact 'Java false-success' P0 class this repo has been bitten by before.

**Failure scenario:** Script: lr.start_transaction("login"); HTTP call throws; catch block calls lr.error_message("login failed"); lr.end_transaction("login", lr.AUTO). The shim emits transaction_end status 0 (PASS), failedRunnerTransactions sees status==0 and skips it, error events don't set err, so result.Success=true — a failing login iteration is reported as fully successful in run metrics and SLA verdicts.

### W4 (HIGH) Network latency simulation now applied only once per connection, so keep-alive requests see zero simulated latency

**Where:** `pkg/protocol/http/network_shaping.go:62` · **Area:** protocol · **Category:** correctness · **Verification:** 2/2 verifiers confirmed

shapedConn previously invoked applyJitterAndLoss (latency + jitter + packet-loss penalty) on every Read/Write. The new shapedDirectionDelay.apply() sets latencyApplied=true on the first read and first write of the connection and never applies latency/jitter/loss again for the lifetime of that net.Conn. Go's default transport keeps connections alive and reuses them across requests (idle timeout ~90s), so in a load test every request after the first on a pooled connection runs with no simulated latency, jitter, or packet loss — only bandwidth shaping remains. **Failure scenario:** Configure web_network_simulation latency 100ms and run a 10-minute test where each VUser issues hundreds of requests over keep-alive connections. The hub run loop no longer unmarshals test_id/project_id from the message payload; routing comes solely from the hubBroadcast struct. startCacheFanout builds that struct from the new envelope fields (envelope.TestID/ProjectID/BroadcastAll). An envelope published by a not-yet-upgraded replica has none of those fields, so the message arrives with testID="" and projectID="" and broadcastAll=false — the client filter (`client.testID != "" && msg.testID != client.testID`) then drops it for every scoped subscriber instead of extracting the ids from the payload as before. Same-version clusters are fine (BroadcastScopedJSON populates the fields).

**Failure scenario:** During a rolling deploy of a multi-replica HA controller, metrics_update messages produced on an old-version replica and fanned out to an upgraded replica never reach that replica's test- or project-scoped websocket clients; dashboards connected to upgraded replicas show stalled live metrics until the deploy finishes.

### W61 (LOW) readJSONLPage predicate-free fast path silently counts unparsable lines outside the requested page

**Where:** `pkg/api/archive_loaders.go:659` · **Area:** perf · **Category:** silent-failure · **Verification:** 1/1 verifiers confirmed

The new fast path for predicate == nil skips json.Unmarshal for rows outside [offset, offset+limit), incrementing `matched` for every raw line. Previously any malformed JSONL line anywhere in the file returned an error. Now a corrupt line outside the current page is silently included in the reported total, and the corruption is only detected if a user pages onto it — so archive transaction/resource totals can overstate row counts and pagination can 500 only on specific pages.

**Failure scenario:** An archive transactions.jsonl with one truncated/corrupt line (e.g. partial write before a crash): the drilldown shows total N including the bad row and pages normally until the user reaches the page containing it, which then errors — before this change the endpoint failed fast and consistently, surfacing the corruption.
