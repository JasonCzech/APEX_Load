### F01 · CRITICAL · Session revocation silently defeated by read-modify-write race on users.session_epoch
**`pkg/api/auth_resolution.go:189`** · Auth proxy/revocation · bug _(independently flagged 2× across Auth proxy/revocation, Admin/RBAC)_

applyLocalUserBindings runs on EVERY authenticated OIDC/trusted-header request (via resolveRequestAuth, and also /auth/me). It loads the full user row with GetUserBySubject (populating local.SessionEpoch), then at line 189 unconditionally calls store.SaveUser(local). SaveUser is an ON CONFLICT(id) DO UPDATE that writes back every column including session_epoch=excluded.session_epoch (sqlite_auth.go:281-282) with no row-version guard. handleRevokeUserSessions -> BumpUserSessionEpoch performs a bare UPDATE users SET session_epoch = session_epoch + 1 (sqlite_auth.go:621). The two statements race last-writer-wins on the same row; a request that read epoch=N before the admin bump but whose SaveUser lands after (epoch=N+1) rewrites session_epoch back to N, reverting the revocation. The stale cookie then passes the check at line 181 again.

**Failure:** An OIDC user actively uses the dashboard (continuous polling => an in-flight authenticated request is almost always present). Admin calls POST /api/v1/auth/users/{id}/revoke-sessions; DB epoch goes 5->6 and returns 200 (audit success). A concurrent request that already read epoch=5 completes applyLocalUserBindings->SaveUser, writing session_epoch back to 5. The revoked cookie (epoch 5) now makes 5 < local.SessionEpoch false and keeps working. An adversary sustaining traffic wins this race indefinitely, so an actively-abused session cannot be reliably revoked, with no signal to the admin.

**Suggested fix:** Do not rewrite session_epoch from the request path: make the auth hot-path a targeted UPDATE of only last_seen_at/display_name/email, or drop excluded.session_epoch from the shared upsert and mutate epoch only via BumpUserSessionEpoch, or gate the write behind an epoch-unchanged WHERE clause.

### F04 · CRITICAL · Harness/Go pair reports success when nothing ran: missing summary, absent lifecycle methods, and int return codes are all ignored
**`runners/java_vuser/Harness.java:47`** · Java sidecar · bug

Three compounding silent-success holes: (1) invokeIfPresent swallows NoSuchMethodException (Harness.java:43-51), so a target class with no public zero-arg init/action/end runs ZERO methods and still prints success:true with duration~0. ### F05 · CRITICAL · Service Bus RequestReply batch receive strands other VUsers' replies (locked, unsettled) and repeated abandons dead-letter them — the shared-reply-queue loss the fix claimed to close persists under contention
**`pkg/protocol/jms/realadapter_servicebus.go:219`** · Fix-commit regressions · bug

588571d6 replaced consume-and-lose with peek-lock+abandon so "a shared reply queue can't drop another VUser's reply"; 0352f0ca changed it to batch ReceiveMessages(ctx, 10, nil) with a 50ms backoff. Two residual loss paths remain: (1) when the correlated reply is found at batch index i, the function returns immediately (line 219) and messages[i+1:] are never completed nor abandoned — they stay peek-locked until the queue's LockDuration expires (Azure default 60s), far past the sibling requesters' default 5s reply timeout; (2) every uncorrelated message is re-abandoned on every receive cycle (line 227), and each abandon increments the broker DeliveryCount, so after MaxDeliveryCount (Azure default 10) the foreign reply is moved to the dead-letter queue and its rightful requester can never receive it.

**Failure:** Real adapter build (-tags jms_servicebus_real), N VUsers doing jms_request_reply against one shared reply queue. ### F10 · HIGH · PostgreSQL backend: last-admin guard count query is never rewritten, permanently blocking admin disable/demote/delete
**`pkg/storage/sqlite_auth.go:613`** · Admin/RBAC · bug _(independently flagged 2× across Admin/RBAC, Postgres dialect)_

CountActiveGlobalRoleHolders uses the alias-qualified predicate `WHERE u.active = 1`. The Postgres dialect rewriter converts the users DDL `active INTEGER NOT NULL DEFAULT 1` to `active BOOLEAN` (pkg/storage/sqlite.go:321) but its predicate rewrite pair is `" active = 1" -> " active = TRUE"` (sqlite.go:328), which requires a leading space and therefore does not match `u.active = 1` (preceded by `u.`). On PostgreSQL the query fails with `operator does not exist: boolean = integer`. wouldOrphanSystemAdmins (pkg/api/handlers_auth.go:1177-1183) deliberately treats a count error as "block", so every disable, hard-delete, PATCH-to-inactive, and global system_admin binding revocation targeting ANY user who holds an active global system_admin binding is rejected with 409 "cannot disable the last active system administrator" — even with many admins.

**Failure:** Enterprise deployment on PostgreSQL with 5 active system admins. Admin A tries to offboard departing admin B via POST /api/v1/auth/users/{B}/disable (or DELETE, or deleting B's global system_admin binding). userHasActiveGlobalSystemAdmin(B)=true -> CountActiveGlobalRoleHolders errors on PG -> wouldOrphanSystemAdmins returns true -> 409 with a misleading 'last active system administrator' message. Admin lifecycle for admins is fully broken on the PG backend; the error is swallowed (no log), so operators only see the wrong 409 text.

**Suggested fix:** Change the query to `WHERE u.active = ?` with s.boolValue(true), or add a rewrite pair for `.active = 1`; add a PG-dialect rewrite assertion test for this query.

# Remediation plan

Phased by risk-to-ship, not by cluster. Every fix must land with tests per the project testing policy (`*_test.go` next to source; table-driven where inputs vary; `go test ./...` before done; dashboard changes verified in-browser, not just tsc). Where a change touches the DSL catalog or API routes, regenerate the derived artifacts (`go generate ./pkg/dsl`, `go generate ./pkg/api`) — freshness is test-enforced.

## P0 — Stop-ship (security & silent-wrong-results). Fix before the next release.

These either break a security guarantee, silently corrupt results, or make a "governance/integrity" feature not govern. Batch them first; each is small-to-medium and independently shippable.

1. **F01 — Session revocation race** (`pkg/api/auth_resolution.go:189`). Stop rewriting `session_epoch` from the request hot path. Make `applyLocalUserBindings` a targeted `UPDATE` of `last_seen_at/display_name/email` only, or drop `excluded.session_epoch` from the shared upsert so only `BumpUserSessionEpoch` mutates it. Test: concurrent revoke-vs-authenticated-request; assert the stale epoch cannot resurrect. Note this also fixes F64/F96/pagination-instability (F65 root) which share the `SaveUser`-on-every-request pattern.
2. **F02 + F49 — Archive integrity self-erasing / no root of trust** (`pkg/api/test_notes.go:67`, `archive_integrity.go:72`). In `syncTestNotesToArchive`, update **only** the `test_notes.json` manifest entry from the known new bytes — never call `updateRunArchiveArtifactIntegrity` (which re-hashes and re-blesses every artifact and drops missing files). Serialize syncs per test (mutex/single-flight, fixes F35). Then give the manifest a root of trust: sign it or record its hash outside the archive dir (e.g. the DB row), and have verify cross-check. Test: tamper an artifact → verify reports tampered → edit a note → verify still reports tampered.
3. **F03 — Secrets archived in cleartext** (`pkg/protocol/evidence.go:213`). Produce a redacted twin of `action.Params` the way Target/Headers/Body already do, or scrub `ProtocolEvidence.metadata["params"]` (and the java_vuser raw stderr/stdout transcripts) in `scrubSensitiveResult`. Test: `{{secret.*}}` in `lr_parameters` never appears in persisted `TransactionEvent` evidence.
4. **F04 + F40 — Java Vuser false success** (`runners/java_vuser/Harness.java:47`, `pkg/protocol/java_vuser/java_vuser.go:267`). Require a summary line (absent summary ⇒ failure), fail when no lifecycle method was invoked, honor `lr.FAIL`/`lr.EXIT_VUSER` return codes, and map `lr.end_transaction(…, FAIL)` to a failed transaction. Test: harness class with no zero-arg method ⇒ run marked failed; a FAIL transaction ⇒ surfaced as failure.
5. **F05 — Service Bus reply loss** (`pkg/protocol/jms/realadapter_servicebus.go:219`). On correlation hit, abandon the rest of the batch immediately (don't leave them peek-locked); track a per-message abandon budget so foreign replies aren't dead-lettered by repeated abandons. Real-adapter (`-tags jms_servicebus_real`) integration test with N contending VUsers on a shared reply queue.
6. **F17 + F18 + F20 — Execution-plan approval bypass** (`pkg/api/execution_plan_governance.go`). (a) Make the approved run actually admit — lift the project VUser gate for the approved test, or the sequential run deadlocks post-approval (F17). (b) Compute peak from the *real* run model: derive stage-driven VUsers and read `GoalConfig.MaxVUsers` (F18). (c) Bind approvals to plan content (hash the plan into the approval) so a mutated plan re-requires approval (F20). Test: over-quota goal/stage plan requires approval; approved sequential plan runs to completion; edited plan invalidates a prior approval.
7. **F10 — Postgres admin lockout** (`pkg/storage/sqlite_auth.go:613`). Change `WHERE u.active = 1` to a parameterized `s.boolValue(true)` (or add the `.active = 1` rewrite pair). Add a PG-dialect assertion test for this query — and close the audit gap F95 (guard test covers only 2 of 3 boolean-rewrite categories) and F96 (case-sensitive user search) in the same pass, since they're the same missed-audit root.
