APEX Load · Product Design audit · 30 September 2026

A coherent theme system,
incomplete coverage of controls.

The overall application has a recognizable visual language. The main problem is uneven adoption of that language: some controls use shared tokens, others use local styling, and some interactive states fall back to the browser. The highest-priority findings are missing keyboard focus and low-contrast warning text. The most visible theme gaps are checkboxes, Governance Audit date inputs, scheduling links and native hover help.

12 findings · 14 reviewed surface groups · all 5 concrete themes sampled. This is a broad audit, not an exhaustive screen-by-theme certification. No application code was changed, configuration submitted, load test started, or existing user work overwritten.

HighF01

Keyboard focus disappears on the theme selector

Confirmed by keyboard and computed styles

Help → Tab from the deployment warning to Dashboard color theme. The selector is focused and matches :focus-visible, but its computed outline style is none and box-shadow is none. Its border retains the normal low-emphasis border. This affects the shared header across the application.

Recommended change. ThemeToggle sets outline: none inline, overriding the shared focus-visible rule. Remove that override and give the closed control a clearly visible theme-token focus treatment. Preserve a visible focus indicator inside the open menu as well.

HighF02

Solarized Light warning text is too faint

Screenshot plus computed contrast

Monitoring’s DEGRADED badge uses 11px text in rgb(181,137,0). Its orange translucent fill over the cream card produces an estimated contrast of 2.39:1 using the computed ancestor backgrounds. This is below the 4.5:1 benchmark for normal text. The warning is harder to read precisely when it needs attention.

Recommended change. Use the semantic warning text/background/border tokens as a matched set instead of using the decorative --warning color as text on a hard-coded orange fill. Check danger, success and info badges across all five themes too; the 2.39:1 measurement applies to this specific badge, not every status.

MediumF03

Checkboxes use two different color systems

Confirmed in rendered controls and DOM styles

Controller & runtime’s Desktop Client Promotion and Client Software Downloads controls have accent-color: auto. Show queued runs in Schedules also keeps the native checked appearance. In Solarized Light the checked box is browser blue despite the olive application accent; in Monokai it remains a native pale check despite the pink accent. Repository checkboxes, by comparison, explicitly compute to the violet theme accent in Dark. Runtime checkboxes are about 13 CSS px, with nearly no gap before Enabled/Disabled.

Recommended change. Give native checkboxes and radios a shared baseline using --accent, consistent dimensions, label spacing, disabled styling and focus behavior. Retain native semantics; a custom replacement is unnecessary just to fix accent color. Preserve explicit destructive-checkbox exceptions.

MediumF04

Governance Audit dates fall back to bare browser inputs

Confirmed across three themes

The From and Until date-time fields are approximately 20.9 CSS px high, white in both Light and Solarized Light and rgb(59,59,59) in Dark. They sit directly against inline labels beside a much larger themed Project scope selector. The surrounding text filters use .settings-input; the date inputs do not. Results Library and the booking dialog already show substantially better themed date-field treatments.

Recommended change. Route date/time inputs through the shared form-field styling: tokenized surface, text, border, radius, spacing, focus and disabled states. MediumF05

Hover help has multiple implementations

Implementation-confirmed; native popup not captured

The inspected sidebar and editor attach help through native HTML title attributes. Those popup tooltips belong to the browser/OS and do not inherit the application palette. Elsewhere, source mapping supplies a CSS data-tooltip bubble and charts use a separate tokenized Recharts tooltip helper. The source-mapping chips also retain title, so two help mechanisms can coexist on a single trigger. Screenshots identify the affected surfaces but do not prove the appearance or timing of a native popup.

Recommended change. Use one application tooltip component for short help with a themed opaque surface, keyboard focus support, an accessible description, Escape dismissal and edge collision handling. Remove redundant title only when equivalent accessible help exists. Keep critical instructions and disabled-action reasons visible or available through a persistent help control.

MediumF06

Settings focus rings retain the default indigo hue

Confirmed by keyboard and computed styles

With Monokai selected, focusing Max Concurrent Tests yields the correct pink border but a fixed rgba(99,102,241,0.18) outer shadow. The same CSS governs text and select fields. Other source styles also contain fixed blue/indigo emphasis. These are separate from the correctly changing theme tokens.

Recommended change. Replace the hard-coded ring with --focus-ring or a derived accent token and standardize focus thickness and offset. Audit focus and selection independently of resting colors; a screen can look themed while its interactive states are not.

MediumF07

Rendered evidence plus source corroboration

In Monokai, Schedule defaults and Capacity commitments and standing allocations inside Scheduled bookings appear as lavender browser-style links. MediumF08

Field labels and control density vary within the same form

Visual consistency finding

Script Library mixes uppercase compact labels (Search scripts, Run release, Folder) with larger sentence-case labels (Assigned application/release). New Test mixes compact uppercase filter labels with larger inline Sort scenarios and Launch application labels. Governance combines placeholder-only text filters with inline date labels. These variations make neighboring controls look as though they come from different products.

Recommended change. Define a small set of deliberate field sizes and one label/hint/error pattern. Apply those patterns within each form and filter toolbar. Give important filters persistent visible labels; aria-label alone does not preserve visual context after typing. Avoid making every control globally the same size regardless of context.

LowF11

Navigation families and empty-state guidance vary

Visual and interaction consistency finding

The app uses filled segmented navigation in the header, underlined result tabs, pill filters in libraries, vertical runtime category buttons, and compact administrative links. These can serve different purposes, but equivalent selection states and sizes are not consistently expressed. Command Center gives an actionable empty state; Results Library tells users to run or pull a result without a matching action in that empty-state panel. Empty Script Library still shows a large filter and table scaffold.

Recommended change. Assign clear roles to page navigation, view tabs, filters and workflow steps, then standardize each family. Keep primary next actions adjacent to empty-state explanations and reduce irrelevant filter/table scaffolding when a workspace has never contained data.

MediumF12

Existing checks do not guard these specific visual states

Source review; tests not executed for this audit

The repository already has theme token tests, select styling tests, theme coverage for Help, and a workflow that visits major routes across five themes and two widths. The reviewed workflow-ux-consistency test checks route headings, theme attributes, toolbar structure and visibility, then saves screenshots. It does not compare those screenshots to expected images or assert the checkbox accent, bare date-field style, closed theme-selector focus ring or this warning badge contrast.

Recommended change. Extend the existing suite with a representative control matrix and focused browser assertions, rather than adding another route-only smoke test. Cover checked/unchecked/indeterminate/disabled controls; empty/filled/invalid text and date fields; select open/closed; native fallback; tooltip hover/focus; and high-risk status contrast. Run the affected flows in dev-admin and local-auth profiles when implementing changes.

Recommended implementation order

  1. Fix the shared accessibility defects: restore the theme selector’s keyboard focus ring and correct semantic status text contrast, starting with Solarized Light.
  2. Finish the control foundation: shared native checkbox/radio baseline; themed text, textarea, number, search and date inputs; consistent labels, hint/error text, disabled and focus states. Exclude checkbox/radio/file controls from generic full-width text-input rules.
  3. Unify help and links: introduce a shared accessible tooltip and text-link pattern, then replace scattered native title help where it adds meaningful explanation. Preserve browser-native selection and editing behavior unless custom behavior is justified.
  4. Resolve page-specific inconsistencies: Governance dates, disabled scenario hover, filter typography, report error recovery and actionable empty states.
  5. Add regression coverage: extend the existing UX consistency workflow with a focused control/state matrix across all five themes and both auth profiles. Include screenshot comparisons where appearance matters, and computed-style/keyboard assertions where they give a more reliable signal.

Evidence limits and verification gaps

  • The initial Dashboard capture uses the existing packaged frontend on :8080. Main inspection uses the running Vite frontend on :4015, verified to serve this repository’s dashboard directory. Source references are from commit e28c4edd plus pre-existing working-tree edits. The working tree was already substantially modified before this audit.
  • All five concrete themes were sampled, but not every route in every theme. System/Auto switching, OS preference changes and cross-browser/native-desktop fallback behavior were not tested.
  • Browser captures included narrow and desktop layouts. Temporary viewport changes produced some incomplete captures; those were rejected. This is not a complete responsive, mobile, zoom, or reflow certification.
  • The accessible DOM and selected keyboard transitions were inspected. No full screen-reader pass, automated accessibility suite, contrast census or WCAG certification was performed. The warning contrast figure is calculated from computed foreground and composited ancestor background colors for one badge.
  • Native title-based help is confirmed in source. Native tooltip bubbles were not captured, and hover timing, clipping and Escape behavior were not comprehensively exercised. The source-mapping tooltip and chart tooltip helpers were source-reviewed, not audited as populated flows.
  • Saved archive DOC-RUN-20260612-002 returned a server error. Populated report charts, chart hover tooltips, baseline comparison, live execution, recording, import repair and external-connection success/error states need a follow-up with representative data. No tests were launched to manufacture those states.
  • Source inspection found 248 checkbox declarations across 73 non-test TSX files and 50 textarea declarations across 29 files. These are maintenance-scope indicators, not counts of defects. The checked manifest, notes and incident-search fields were themed; not all freeform fields are broken.
  • This was an audit-only pass. Existing tests were inspected but not run or changed. Implementation should follow the repository’s unit, lint, typecheck and browser requirements.
