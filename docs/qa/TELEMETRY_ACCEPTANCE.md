## Reference workload

`APEXLOAD_TELEMETRY_REFERENCE=1 go test ./pkg/api -run '^TestTelemetryReferenceWorkload$' -v` runs the TEL-4 reference workload in one process: two declared generators (real generator services reached over in-memory gRPC) each run half of `APEXLOAD_TELEMETRY_REFERENCE_RATE` (default 2,000) accepted observations a second against a local target for `APEXLOAD_TELEMETRY_REFERENCE_SECONDS` (default 60), publishing every second. While it runs, a foreground dashboard (headless Chromium on the run's live page, reporting its render evidence) watches it, and archive analyses of an earlier run are read every second. It records each stage's P50/P95/P99 and maximum, the run's coverage and loss accounting, the target's own count of served requests against the archive's samples (unreported loss), clock uncertainty, process CPU and peak RSS, and every failure.

Stage percentiles are never added. The sum of the sample-age and browser-render maxima is recorded, but it leaves out delivery from the controller's publication to the browser's receipt, so it does not bound capture to visible render. Loss is accounted per path: the archive's samples, and separately the run's live totals (successes and recorded errors) plus its dropped-results counter, must account for every served request but those aborted in flight at the stop (at most one per VUser); a counter that is only a lower bound is noted. Lost publications and dropped subscriber batches are counted in publications, and a dropped batch is also a lost sequence: each lost publication may account for at most the largest window one generator's group published, and a shortfall within that is reported loss of unknown size, classified `live_publications_lost`. A run fails with unreported loss on either path, more results than were served on either path (duplicates), no sample-age P99 (an unqualified clock is classified `clock_unqualified`), a sample-age P99 above 2,000 ms, no browser-render evidence, an accepted rate under 90% of the workload (archived samples over the load window, first to last sample), a failed analysis, or a stop before it was measured; render alone over the target is classified `slow_browser`. With `APEXLOAD_TELEMETRY_REFERENCE_OUT` it writes `telemetry-reference.json`, and, when `APEXLOAD_COMMIT_SHA` names the measured commit, one F4 request (`TEL-4`, `telemetry-reference`): `pending` without failures, `failed` otherwise, never `passed` by itself. `scripts/run-optin-suites.sh --all` runs it as the "telemetry reference workload" suite. It does not exercise collector traffic, an overload trial, generators on other hosts or native (DuckDB) analytics, it does not record queue or byte volumes, and it is not the 4 vCPU / 16 GiB reference controller.
