Each BE-4 behavior names the tests that accept it. **Chromium and WebKit** tests drive controlled pages in both engines; **Unit** tests exercise the same code without a browser (simulated CDP or WebKit events, files and budgets). ## Benchmark

`APEXLOAD_BROWSER_BENCHMARKS=1 go test ./pkg/protocol/browser -run '^TestBrowserBenchmark$' -v` measures each engine with a desktop and a mobile profile it accepts (Chromium: `desktop_1080p`, `pixel_8`; WebKit, which has no desktop profile: a 1920x1080 viewport, `iphone_15_pro`). Each runs five sessions in each of three modes: plain, document capture, and 200 ms of network latency. It records:

- the host (OS and kernel version, CPU model and count, memory), the Playwright driver version and each browser's version;
- cold launch (the engine's browser started from nothing) and session start against the pooled browser a generator keeps running;
- navigation time, the overhead of document capture, and the throttled navigation's separation from the plain one;
- peak RSS and CPU seconds of the Playwright driver and browser process tree;
- teardown time, and processes left once the browser closes;
- failures.

It writes `browser-benchmark.json` to `APEXLOAD_BROWSER_BENCHMARK_OUT`. When `APEXLOAD_COMMIT_SHA` names the measured commit, it also writes `browser-benchmark-acceptance-requests.json`: one F4 feature acceptance request per engine and profile (`BE-4`, `browser-benchmark`), naming the results' SHA-256. An operator posts the requests to `/api/v1/system/acceptance-records`.

The published five-browser-VUser ceiling stays until reviewed evidence authorizes more. Synthetic shaping is a calibrated approximation, not a device equivalence claim.
