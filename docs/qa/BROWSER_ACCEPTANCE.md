# Browser acceptance

Generated by `docs/qa/browser_acceptance_test.go` (BE-4). Regenerate with `APEXLOAD_UPDATE_BROWSER_ACCEPTANCE=1 go test ./docs/qa -run TestBrowserAcceptanceInventory`.

Each BE-4 behavior names the tests that accept it. **Chromium and WebKit** tests drive controlled pages in both engines; **Unit** tests exercise the same code without a browser (simulated CDP or WebKit events, files and budgets). The browser package's real-browser tests need installed Playwright browsers: without them they skip, or fail under `APEXLOAD_BROWSER_TESTS=require`. `scripts/run-optin-suites.sh --all` runs the browser package with both engines required and the acceptance benchmark, keeping the benchmark results, as the "browser acceptance" suite.

## Benchmark

`APEXLOAD_BROWSER_BENCHMARKS=1 go test ./pkg/protocol/browser -run '^TestBrowserBenchmark$' -v` measures each engine with a desktop and a mobile profile it accepts (Chromium: `desktop_1080p`, `pixel_8`; WebKit, which has no desktop profile: a 1920x1080 viewport, `iphone_15_pro`). Each runs five sessions in each of three modes: plain, document capture, and 200 ms of network latency. It records:

- the host (OS and kernel version, CPU model and count, memory), the Playwright driver version and each browser's version;
- cold launch (the engine's browser started from nothing) and session start against the pooled browser a generator keeps running;
- navigation time, the overhead of document capture, and the throttled navigation's separation from the plain one;
- peak RSS and CPU seconds of the Playwright driver and browser process tree;
- teardown time, and processes left once the browser closes;
- failures.

Each engine is a subtest, so an engine missing from the host skips or fails alone and the other's results are still written. It writes `browser-benchmark.json` to `APEXLOAD_BROWSER_BENCHMARK_OUT`. When `APEXLOAD_COMMIT_SHA` names the measured commit, it also writes `browser-benchmark-acceptance-requests.json`: one F4 feature acceptance request per engine and profile (`BE-4`, `browser-benchmark`), naming the results' SHA-256. A request is `pending` for a reviewer to judge against the published targets (launch, action overhead, RSS per VUser), or `failed` when sessions failed, processes were left or throttling did not separate; it never claims a pass by itself. Navigation time is absolute, not an overhead against a baseline. An operator posts the requests to `/api/v1/system/acceptance-records`. The Go benchmarks (`BenchmarkBrowser*`) the browser benchmark evidence names run with their own command.

The published five-browser-VUser ceiling stays until reviewed evidence authorizes more. Synthetic shaping is a calibrated approximation, not a device equivalence claim.
