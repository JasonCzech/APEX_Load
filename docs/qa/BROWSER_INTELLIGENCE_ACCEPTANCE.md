# Browser intelligence acceptance

Generated by `docs/qa/browser_intelligence_acceptance_test.go` (BI-4). Regenerate with `APEXLOAD_UPDATE_BROWSER_INTELLIGENCE_ACCEPTANCE=1 go test ./docs/qa -run TestBrowserIntelligenceAcceptanceInventory`.

Each BI-4 golden behavior names the tests that accept it. **Chromium and WebKit** tests drive controlled pages in both engines; **Chromium** tests cover an API only Chromium exposes (the Layout Instability API); **Unit** tests exercise the same code without a browser. Real-browser tests need installed Playwright browsers. The golden runs only with `APEXLOAD_BROWSER_TESTS=require`; the other real-browser tests run whenever an engine is installed and skip when it is missing, unless `APEXLOAD_BROWSER_TESTS=require` makes a missing engine a failure. `scripts/run-optin-suites.sh --all` runs the golden in both engines as the "browser intelligence acceptance" suite.

These Playwright tests run in both authentication profiles (default and local-auth).

## The golden

`APEXLOAD_BROWSER_TESTS=require go test ./pkg/api -run '^TestBrowserIntelligenceGoldenAcceptance$' -v` runs a controlled page in Chromium and WebKit: a hero image the fixture server holds for 300 ms, three layout shifts in two session windows, three synthetic taps on one action, and a wait for a confirmation that never appears. The page's real document and interaction evidence and its actions' results go through the archive writer (the document evidence three times: a mid-run snapshot, then the final evidence twice), and the archive is read by the code that serves findings, interaction patterns and journeys. It checks:

- each document metric against the page's own PerformanceObserver entries: CLS equals the largest session window (which differs from the sum of shifts), LCP and FCP equal their entries within 1 ms, and LCP is no earlier than the server's hold;
- a metric missing from the engine's `PerformanceObserver.supportedEntryTypes` is unavailable as `unsupported`, never a value, its finding is unscored, and the run's score is unscored with that metric missing (WebKit has no Layout Instability API);
- the blank document a context starts with carries no value;
- the repeated publications are counted once, without a collection-health finding;
- the findings and score under a policy that makes the held hero and the shifts poor and FCP good;
- one scripted-repetition pattern of three taps, all excluded from heatmaps as synthetic dispatch;
- one failed checkout journey attempt and a weighted failure index of 1;
- the fixture server saw the page and its hero once each: capture and analysis added no target traffic.

With `APEXLOAD_BI_ACCEPTANCE_OUT` it writes `browser-intelligence-golden.json` there. When `APEXLOAD_COMMIT_SHA` names the measured commit, it also writes `browser-intelligence-acceptance-requests.json`: one F4 feature acceptance request per engine (`BI-4`, `browser-intelligence-golden`), naming the results' SHA-256. A request is `pending` when the engine's golden held, for a reviewer to record against a release binary, and `failed` when it did not; it never claims a pass by itself. An operator posts the requests to `/api/v1/system/acceptance-records`. Baseline regressions are accepted by unit tests over seeded series: no two real runs at different load levels are compared here.
